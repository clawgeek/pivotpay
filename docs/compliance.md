# 合规边界与实现声明

本项目是**支付系统工程架构的教学/毕业设计实现**，用于演示领域驱动设计、高可用路由、幂等与一致性机制。它不是可直接用于真实收款的收单产品。

## 一、明确实现的能力

- 多租户 SaaS 控制台：商户/应用/凭据管理、租户级数据隔离
- 商户开放 API：HMAC-SHA256 签名、时间戳窗口、nonce 防重放、幂等下单
- 支付主链路：下单 → 加权健康度通道路由（含 failover）→ 收银台凭证 → 通道回调验签 → 订单状态推进
- 资金一致性：复式记账、退款冲回、借贷平衡校验、Outbox 事务性事件、日终对账与差异登记
- 高可用：三态熔断、健康分、故障注入演练台、Webhook 指数退避与死信队列
- 可观测性：审计日志、Trace ID、健康检查、运行指标

## 二、明确不实现的能力

三个参考视频中出现的以下玩法属于规避支付监管的高风险做法，**本项目一律不实现、不预留接口、不提供文档指引**：

| 玩法 | 风险 |
| --- | --- |
| 个人收款码「免签」监听（监听手机通知/轮询账单） | 无持牌受理、资金流不可审计、易被用于洗钱与诈骗 |
| 异地收款 / 跳转规避风控 | 绕过支付机构商户地域与场景管控 |
| 发卡通道 / 第四方资金池 / 二清 | 无支付业务许可证的实质资金清算，违法违规 |
| 代收代付、跑分、租借商户号 | 为灰黑产提供资金通道 |

## 三、通道策略

| 类型 | 数量 | 状态 |
| --- | --- | --- |
| 沙箱模拟通道（`mock_*`） | 4 | 可直接下单演练；生成伪造二维码/链接凭证，不产生真实交易，含可控失败率、延迟与故障注入 |
| 持牌通道占位（`official_*`） | 3 | 支付宝开放平台 / 微信支付 / 银联全渠道：仅实现 `ChannelAdapter` 接口形状与配置位，`isConfigured()` 恒为 false，默认停用，调用直接返回 503 `CHANNEL_NOT_CONFIGURED`，**不发起任何真实网络请求** |

接入真实持牌通道的前置条件（本项目不代劳）：企业营业执照与对应行业资质、支付机构商户进件与审核、官方开放平台应用与密钥、合规的回调域名与备案、对账与清算文件通道、PCI DSS / 等保相关要求。

## 四、演示数据说明

- 所有商户号、API Key/Secret、订单、金额、二维码均为**本地生成的沙箱数据**；二维码是确定性 SVG 图案，不可扫码支付。
- 数据库文件 `data/pivotpay.db` 仅存本地；删除后重启会重新生成确定性种子数据。
- 「商户与密钥」页面出于演示目的明文展示 Secret，**生产系统严禁如此**：应使用 KMS 托管、不可逆哈希存储、密钥轮换、最小权限授权与操作审计。
- 控制台用 `X-Tenant-Id` 请求头模拟租户身份，仅用于本地演示；生产必须替换为 SSO + JWT + RBAC，否则可被伪造跨租户访问。

## 五、部署提示

`npm start` 默认监听 `127.0.0.1:3001`（仅本机）。如需对外提供服务，请自行配置反向代理、TLS、WAF、限流与鉴权，并完成安全评估。项目默认关闭 CORS 限制（`origin: true`）也是为本地演示方便，生产应收紧白名单。
